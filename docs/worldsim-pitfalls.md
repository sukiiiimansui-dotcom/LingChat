# 移动端 WebGL / 3D 网页：常见技术陷阱（可独立复现）

这份记录面向"做过 WebGL/地图/三维网页，但可能没踩过这些坑"的开发者。
每条只讲**通用机制**，都给出**最小复现思路**与**判定方法**，不依赖任何具体项目的代码。

---

## 1. 初始化顺序：默认值参与了"切换判据"

**场景**：页面有多个渲染后端（2D 地图 / 3D 叠加层），用"当前偏好 ≠ 当前后端"来决定是否切换。

**陷阱**：如果"当前后端"的初值被设成了**偏好**的默认值，两者从一开始就相等，切换逻辑**一次都不会触发**——表现为"3D 永远不出现"，且日志里看不到任何报错。

**最小复现**：
```js
const DEFAULT = "3d";
let pref = ref(DEFAULT);
let live = ref(DEFAULT);        // ← 初值写成了目标值
watch([pref, live], () => { if (pref.value !== live.value) swap(); }); // 永不成立
```

**判定**：打印 `pref` / `live` / 切换次数；若 `live` 一开始就等于目标值而实际没建对象，即是此坑。

**解法**：`live` 从"实际已启动的那个后端"起（例如 `"2d"`），切换只由"偏好变化"驱动；并用一个显式的 `switches` 计数佐证。

## 2. 顶点色的 sRGB / 线性：多了一次 gamma

**场景**：用 CSS 十六进制颜色生成 WebGL 顶点色，渲染器默认 sRGB 输出。

**陷阱**：着色器把顶点色当**线性**值，输出时再做一次 sRGB 编码。若输入本身就是 sRGB（CSS 色），等于做了两次编码——整体**变亮、发灰**，且你调色板时"怎么调都没用"。

**最小复现**：
```js
// sRGB 0.37 → 直接当线性 0.37 → 输出时编码成 sRGB ≈ 0.64（明显更亮）
gl.bufferData(gl.ARRAY_BUFFER, new Float32Array([0.37, 0.52, 0.71]), gl.STATIC_DRAW);
```

**判定**：把一个已知色值同时写进顶点色与一个 CSS 色块，截图比像素；若顶点色总是更亮，即是 gamma 问题。

**解法**：顶点色入口统一 `srgbToLinear(c)`（`c<=0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4`）；或显式关闭输出编码（不推荐，会影响贴图）。

## 3. WebGL 上下文丢失：不 `preventDefault` 就不会恢复

**场景**：移动端 GPU 驱动重置、系统回收显存、页面长时间后台后，画布黑掉。

**陷阱**：`webglcontextlost` 事件里不调用 `preventDefault()`，浏览器**不会**尝试恢复；同时"恢复后重建资源"的代码若没有做幂等（比如重复调用 `addSource/addLayer`），会抛一堆 `already exists`，外层看门狗据此判定"永久失败"并把画布销毁。

**最小复现**：
```js
canvas.addEventListener("webglcontextlost", (e) => {
  // 缺 e.preventDefault() ⇒ 浏览器不会触发 restored
});
```

**判定**：监听两个事件并计数；丢失后 `restored` 永远为 0。

**解法**：`preventDefault()` + 主动请求恢复（`WEBGL_lose_context.restoreContext()`，带有限次退避）+ 所有资源重建/重放**幂等**（按 id 去重，不重复添加）。

## 4. Chromium：GPU 光栅 + GPU 合成同时开启时，DOM 文字消失

**场景**：Chromium 内核（含部分 Android WebView）同时开启 GPU 光栅与 GPU 合成（这是默认配置）。

**现象**：页面"看起来白屏"，但 WebGL 与 canvas 内容都在；**所有 DOM 文字消失**（HUD、气泡、对话框正文不可见，只剩背景块）。

**实测条件**：Chromium 149 / 155 均复现；同机 Firefox 不复现；**只要光栅或合成任一项走软件即恢复正常**。

**判定**：统计文字条带内"相邻像素亮度差 > 20"的比例——有字约 0.19–0.24，无字 0.005–0.01；同时看 `chrome://gpu` 里 Rasterization / Compositing 的状态。

**规避**：`--disable-gpu-rasterization`（WebGL 仍硬件加速）；或 `--disable-gpu-compositing`（WebGL 会降为 reduced performance，不建议）。

**注意**：真机 WebView 走原生 GLES 驱动，与本机 Mesa/virgl 模拟层行为不同，**必须分环境验证**。

---

## 5. ANGLE 后端与 `libGLESv2` 不匹配

**现象**：`--use-angle=gl` 启动时报 `Initialization of all (0) EGL display types failed`，GPU 进程退出；`--use-angle=swiftshader*` 可以但性能极差。

**根因**：`libGLESv2.so` 被替换成了只编译了 Vulkan 后端的 ANGLE 变体（常见于"把桌面 ANGLE 拷进移动包"或旧实验残留）。

**判定**：`dpkg -V <browser-pkg>` 报 `?M5`；`chrome://gpu` 的 GL implementation 不是预期的 `angle=opengl`。

**解法**：用发行包内原始库覆盖回去；包升级后会再次覆盖，复现前先校验。

---

## 6. `maxCanvasSize` 压缓冲后，用 `canvas.width` 当 CSS 尺寸

**陷阱**：某些库会把绘制缓冲压到上限（如 2048），而画布 CSS 盒更大（如 2280）。此时 `canvas.width / devicePixelRatio` **不等于** CSS 宽高；凡是拿它算"视口边界/命中范围"的逻辑都会误判。

**判定**：`canvas.width/height` 与 `canvas.getBoundingClientRect()` 对比，比例不是 1。

**解法**：视口一律取 `clientWidth/clientHeight`（CSS 口径）；缓冲尺寸只用于像素级采样。

---

## 7. DOM 叠层被后插入的 canvas 容器盖住

**陷阱**：地图/3D 库把 `canvas-container` **追加**为主容器的**最后一个子节点**。若你的 HUD 也 `z-index:auto`，它会被画布按树序盖住——DOM 存在、`getBoundingClientRect()` 正常，但**看不见**。

**判定**：把目标元素背景改成醒目色并统计该矩形内的像素——着色为 0 即被盖住；给 `z-index` 后立刻出现。

**解法**：显式 `z-index`（注意别影响交互与 `pointer-events`）；或把这类覆盖层挂到更外层容器。

---

## 8. 相机俯仰时，画布远端透明会透出容器底色

**现象**：浅色主题下画面顶部出现一条深色带。

**机制**：相机俯仰后地图平面在远端被裁掉，那一块画布是**透明**的，透出的是容器 CSS 背景色；很多地图库的"天空"层只在 globe/atmosphere 模式下生效。

**判定**：把容器底色改成洋红，统计顶部条带里的洋红像素；若与"深色带"面积一致，成因即确认。

**解法**：容器底色跟随主题（含夜间变体）；或在 3D 层补一个天空色块/大背景面。

---

## 9. 画布内的黑色几何块（成因未定）

**现象**：特定机位、特定缩放下，画布内出现一块黑色区域叠加成排白色三角。

**排查顺序**：先隐藏整块画布确认归属；再逐层隐藏图层；再换 `maxCanvasSize` / DPR / 缩放级别；最后对比不同浏览器。

**阻塞点**：自动化截图在不同状态下可能返回**同一帧**（见 §15），导致 A/B 结论不可信——这类问题应优先保证"取图可靠"再二分。

---

## 10. rAF 计数 ≠ 出帧数

**陷阱**：很多 HUD 用 `requestAnimationFrame` 频率当 fps。地图静止时**根本不重绘**，rAF 仍以 60Hz 触发 ⇒ 显示 50–60fps，但实际 0 帧。

**判定**：监听 `map.on('render')`（或渲染器每帧回调）计数；静止 4 秒内为 0 即验证。

**解法**：HUD 同时显示"rAF 频率"和"绘制帧间隔"，性能结论只用后者。

---

## 11. 拖动期间的每帧绘制成本

**判定方法**：不移动相机、只调用一次 `triggerRepaint()`，测单帧耗时；若仍然几十到上百毫秒，说明瓶颈在**每帧绘制本身**（图层数、着色器、驱动），而不是数据/业务逻辑。

**排除法**：依次关掉叠加层、标签层、非必要图层；调 `maxCanvasSize`/DPR；观察拖动期间是否有新的瓦片请求。

**经验**：在软件模拟层（virgl/llvmpipe）上，单帧 85–143ms 很常见；真机原生驱动通常好得多，**结论必须分环境**。

---

## 12. 全局手势特效叠加在拖动手势上

**陷阱**：站点级的"点击/触摸特效"库往往在 `window` 上挂捕获阶段的 touch 监听，并在每次事件里做 `gl.getError()` 之类的重操作。实测一次拖动可触发数千次，自耗数秒。

**判定**：profile 里该库的 self-time；关掉特效后对比（注意负载噪声，A/B 至少跑 3 次）。

**解法**：在地图容器上按 `inputFilter`/`stopPropagation` 排除；或把特效限制到非地图区域。

---

## 13. "降 DPR / 降画布尺寸"不是默认答案

**实测**：`maxCanvasSize` 1024 与 2048 帧率几乎相同；`pixelRatio` 调整同样无收益。原因是瓶颈在每帧绘制与驱动，而非填充率。

**建议**：先把 §10/§11 的量测做出来，再决定要不要降。

---

## 14. MVT / 矢量瓦片的 512px 口径

**陷阱**：瓦片 z/x/y → 米/像素换算若按 256px 算（`156543`），数值会差 2 倍。MapLibre 等库按 **512px** 瓦片（`40075016.686 / 512 = 78271.5`）。

**判定**：同一经纬度用库的 `project()` 与自算值对比。

---

## 15. `querySourceFeatures` 对矢量源必须给 `sourceLayer`

**陷阱**：不传 `sourceLayer` 时通常**静默返回 0 条**（无异常）。

**判定**：同一视野传/不传的返回条数对比。

---

## 16. 生成物（瓦片/快照/vendor）的指纹 gate

**场景**：主题、参数或数据变了，但预渲染产物是旧的。

**陷阱**：只改源、不重建产物 ⇒ 指纹对拍恒红；反过来，重建产物若不重跑页面侧校验，可能暴露页面侧的历史问题（如重复处理）。

**判定**：`--check` 的差异数；把产物重生成到临时目录后指纹是否等于断言值。

**解法**：把"改主题/数据 ⇒ 必须重建产物"写进提交检查清单；产物重建后**同时**跑页面级校验。

---

## 17. 生成物与源码漂移（vendor 类）

**陷阱**：`vendor/*.mjs` 之类的"预构建产物"长期不更新，源码已大幅变化，但页面仍跑旧产物；症状是"源码里明明有某字段，页面上看不到"。

**判定**：产物与源码的字节数/哈希；页面读到的接口与源码导出是否一致。

**解法**：重建产物；并确保"产物重建"与"页面侧逻辑（幂等/兼容）"一起验证。

---

## 18. 分支历史不共祖

**陷阱**：两条分支没有共同祖先（`git merge-base` 退出码非 0）时，一批提交在 A 分支而不在 B 分支，表现为"多份校验在 B 上恒红"。

**判定**：`git merge-base <a> <b>`、`git rev-list --count a..b` / `b..a`。

**解法**：要么移植，要么**正式弃用**并在断言里保留原文 + 自动复活门（对象真消失时自动切回严格口径）。

---

## 19. CI：`matrix` 上下文不能用在部分字段

**陷阱**：
- `continue-on-error: ${{ matrix.xxx == 'y' }}`
- `jobs.<id>.if` 里引用 `matrix`

以上都会让**整份 workflow 校验失败**，表现为"以文件路径命名的失败 run"，而不是某一步失败——极易误判。

**判定**：Actions 列表里出现文件名作为 run 名。

**解法**：从矩阵里删除对应项（或拆成独立 job），不要用条件跳过。

---

## 20. 分支/PR 上无 macOS runner

**现象**：macOS job 排队约 15 分钟、一个 step 都没执行就被取消，整条流水线红。

**判定**：job `conclusion=cancelled` 且 `steps` 为空。

**解法**：矩阵移除 macOS；iOS/macOS 构建改为定时或手动触发。

---

## 21. 无头/容器里 geckodriver 需要可写 TMPDIR

**现象**：`Process unexpectedly closed with status 1`，Firefox 一启动就退。

**根因**：geckodriver 把临时 profile 写到 `/tmp`，该环境不可写。

**判定**：geckodriver 日志里的 `rust_mozprofile…` 创建失败。

**解法**：启动 geckodriver 时显式 `TMPDIR=<可写目录>`；GL 相关环境变量也放在 geckodriver 的 env 里（子进程继承）。

---

## 22. WebDriver 截图可能返回同一帧

**陷阱**：不同页面状态下 `screenshot` 返回**字节完全相同**的 PNG（合成器缓存/软件路径导致）。

**判定**：多次截图后比较 `md5`，与页面实际变化是否一致。

**替代**：X11 下 `import -window root` 抓真屏；页面内 `preserveDrawingBuffer:true` + `toDataURL()` 自查。

---

## 23. 软件渲染会给出"误导性的全绿"

**陷阱**：无 GPU 的环境里，某些视觉/性能相关的自检会通过，但真机行为不同（各向异性过滤、纹理尺寸、合成路径等）。

**判定**：`WEBGL_debug_renderer_info` 的 renderer 串（`SwiftShader` / `llvmpipe` / `virgl` / 真 GPU）。

**建议**：视觉与性能结论只在真 GPU 路径下判定；软件路径只用于结构/逻辑校验。

---

## 24. 进程判断：`pgrep -f` 会匹配到自身

**陷阱**：脚本里用 `pgrep -f "<关键词>"` 判断"某服务是否在跑"，而脚本自己的命令行里就含有该关键词 ⇒ 判定恒真，甚至会把自己杀掉。

**解法**：读 `/proc/*/cmdline` 并排除自身 PID；或按进程名取（`ps -o pid= -C <comm>`）。

---

## 25. 注释里出现 `*/` 会提前闭合

**陷阱**：在 `/* … */` 里写了 `facade*/…` 之类的文本，注释被提前闭合，报错指向看似正常的行。

**解法**：注释里避免连续 `*/`；必要时用 `* /` 或改措辞。

---

## 26. 并行跑同一套自检会互相污染

**陷阱**：两份校验同时读写同一临时目录/生成物，出现"偶发失败、单跑全绿"。

**解法**：串行执行；或每组用独立临时目录/端口。

---

## 附：通用的验证口径

| 类别 | 该用什么数 |
| --- | --- |
| 渲染器身份 | `WEBGL_debug_renderer_info` 的 renderer 串；`chrome://gpu` 的 Rasterization/Compositing |
| 视觉改动 | 同一探针在改色前后的**像素计数**（不是"看起来变了"） |
| 性能 | `map.on('render')` 的计数与间隔（不是 rAF）；`performance.now()` 分段 |
| 生成物 | `--check` 差异数、指纹与断言值对照、逐字节对拍 |
| CI | run 名 / 退出码 / job 的 steps 列表（区分"校验失败"与"步骤失败"） |
